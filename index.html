01

Quick start

Your first useful run

Use the development fixture to learn the controls, or enter any Hugging Face causal language model ID. Graph inspection needs only checkpoint metadata; prompt-conditioned analysis needs an execution worker.

Bring
  • A public Hugging Face model ID—or a read token for a private or gated model.
  • A local worker or Daytona GPU only when you need real activations and interventions.
  • One selected prompt, one meaningful reference prompt, and a metric that represents the behaviour.
  1. 1

    Open the checkpoint

    Launch the workspace and choose Open GPT-2 example, or enter a repository ID and revision. ModelDebugger inventories the repository, reads safe headers or manifests when available, and falls back to a visibly partial configuration scaffold.

  2. 2

    Orient yourself in the graph

    Use search, zoom, and fit-to-view. Click a node for its role, connections, exact tensors, shard order, shapes, dtype, and raw metadata.

  3. 3

    Attach execution

    Open Settings → Execution worker. Add your Daytona API key to start a managed GPU, or run the local worker in another terminal. Connect, then choose Load current model.

    make -C '/Users/maximiliannicholson/Documents/untitled folder 5' worker
  4. 4

    Define the experiment

    Open Run model. Set the selected prompt, reference prompt, expected behaviour, target token, seed, and metric. A logit difference or target probability is often clearer than an unqualified “looks better.”

  5. 5

    Run and save

    Choose Run selected example. Read predictions, tokenisation, attribution, residual traces, attention entropy, hook inventory, and diagnostics. Save the setup as a debug case before changing it.

02

Interpretation rules

Know what kind of evidence you have

ModelDebugger separates the map, the measurements, and the manipulations. Treating them as interchangeable is the fastest route to an overclaim.

MAP

Structural

Configuration, tensor names, shapes, shard order, graph paths, and inferred module roles.

Answers: what exists?Useful for navigation, not behavioural causality.
MEASUREMENT

Observational

Predictions, residual norms, DLA, attention entropy, token alignment, and divergence maps from a hooked run.

Answers: what co-varies?Suggests candidates; it does not prove necessity.
MANIPULATION

Causal

Ablations, activation patches, resampling, scaling, steering, and intervention-backed pruning.

Answers: what changes the result?Valid only for the tested prompts, metric, component, and intervention.

Graph anatomy

Read left to right, then inspect depth.

Nodes represent computations or parameterised modules. Arrows show data flow; the residual rail carries the accumulating hidden state through the model. Transformer blocks group repeated attention and MLP operations.

Stacked cards
The offset cards behind a node encode tensor rank—the number of dimensions—not duplicate modules. The stack now stays inside its owning container.
Tensor order
The inspector records forward-pass-relevant parameter order and original shard position. It is provenance, not an execution timestamp.
Measured badges
Values appear only after a compatible hooked run. A dash means “not measured,” never zero.
Predictions
Inferred architecture labels are explicitly marked. Check the model implementation before treating them as ground truth.
03

Worked from end to end

Three journeys through one real debug case

These are not mockups. Every screenshot below was captured from ModelDebugger while a local worker ran openai-community/gpt2 in float32. Follow the same case from checkpoint structure to a measured decision about whether an intervention worked.

CAPTURE CONTEXT

Selected: “The capital of France is” · Reference: “The capital of Germany is” · Target: “ Paris” · Metric: target-token probability. The values are a pedagogical run, not a general finding about GPT-2.

FLOW 01 · STRUCTURE → PERFORMANCE

Profile a prompt before debugging its mechanism

First establish what was loaded, what was actually measured, and where the worker spent time. This catches checkpoint mismatches and instrumentation overhead before they are mistaken for model behaviour.

  1. Open the GPT-2 fixtureConfirm the resolved revision, tensor inventory, parameter count, and twelve decoder blocks.
  2. Attach the local workerLoad the same checkpoint and run the selected prompt once with hooks enabled.
  3. Read the waterfallSeparate preparation, tokenisation, transfer, instrumented forward, analysis, and retention from browser round-trip time.
DECISION

The run is interpretable.

The checkpoint and worker model match, the prompt tokenisation is visible, and phase-level timings are available. Continue to paired evidence; do not interpret latency as component importance.

FLOW 02 · OBSERVE → INTERVENE

Localise a difference, then try to falsify the candidate

A paired comparison ranks where the selected and reference runs differ. The intervention then asks the stronger question: does manipulating one candidate change the declared behaviour metric?

  1. Compare matched promptsInspect token alignment before the divergence map so lexical differences stay visible.
  2. Select a candidateThis run ranked the layer-9 residual output highly; ranking is observational and only proposes a test.
  3. Zero the final-token writeHold the prompt, target, and metric fixed, then measure the clean-to-intervened effect.
DECISION

Reject this candidate as a fix.

A large target-logit movement or KL divergence is not the same as improvement on the predeclared metric. The manipulation is causal for this exact run, but the result does not support the claim that zeroing layer 9 fixes the behaviour.

FLOW 03 · VERIFY → REPORT

Make the app earn the word “fixed”

Replay the latest candidate on the selected case and guardrail prompts. Position-scoped interventions follow the final token across different prompt lengths, while the model, metric, component, and manipulation stay fixed.

  1. Add guardrailsUse prompts whose target behaviour must not regress, one per line.
  2. Verify the candidateCompare each prompt with and without the saved intervention under the same metric.
  3. Export the recordKeep the exact prompts, revision, tokenisation, worker context, intervention, and claim boundary together.
DECISION

Report “unchanged,” not “fixed.”

This negative result is useful: it closes one causal hypothesis without manufacturing a success. Try a better-matched activation patch, another component, or a revised metric, then rerun the same guardrails.

05 · OBSERVATIONAL

Compare selected and reference prompts

Use this when one prompt produces the behaviour and a closely matched control does not.

Before you begin

Load the model into a worker. Keep the prompts as similar as the hypothesis allows, define the target or token groups, and select the metric before running.

  1. Enter the selected prompt and reference prompt in Run model.
  2. Run the selected example, then choose Compare with reference.
  3. Check token alignment first; mismatched tokenisation can move apparent divergence.
  4. Read the metric delta and ranked internal divergence map together.
  5. Carry a short candidate list into an intervention—do not stop at correlation.
How to read it

Large KL or activation divergence identifies where runs differ, not why the output changed. Direct logit attribution is signed observational evidence: positive supports the target in that run; negative opposes it.

06 · CAUSAL

Test a component with an intervention

Use this to test whether a candidate component is necessary, sufficient, or directionally influential for the defined metric.

ZeroRemove the activation.MeanReplace it with a baseline mean.ResampleInsert a control activation.PatchCopy the matched reference activation.ScaleChange its magnitude.SteerAdd a selected direction.

Choose deliberately

Patch, resample, and steering need comparison context. Select one component, choose the selected token or all positions, and record the scale. Position-scoped tests are usually easier to interpret.

  1. Run or compare the case so captured components are available.
  2. Select the candidate and intervention method.
  3. Set scope and scale, then choose Run intervention.
  4. Compare the intervened metric to the clean selected run.
  5. Repeat with controls, nearby components, and seeds before claiming specificity.
Claim boundary

A signed effect is causal for this exact manipulation and context. It does not automatically establish the component’s natural mechanism, uniqueness, or general importance.

07 · CAUSAL DISCOVERY

Trace a candidate root-cause circuit

Use this after paired comparison when you need a smaller intervention-backed subgraph rather than a long ranked list.

EAP → ACDC

Edge attribution patching quickly ranks candidate computation edges. ACDC then uses actual activation interventions to prune edges whose removal stays below your metric threshold.

  1. Create a clean selected/reference comparison with a meaningful metric.
  2. Choose the candidate count; begin small enough to audit.
  3. Set the ACDC threshold in metric units.
  4. Choose Discover candidate circuit.
  5. Inspect retained edges, fidelity, and stability; rerun across examples and thresholds.
How to read it

Fidelity asks whether the reduced circuit preserves the measured effect. Stability asks whether the result survives perturbations. Neither replaces external replication or guardrail verification.

08 · BOUNDED INSPECTION

Inspect one activation slice

Use the microscope when summary charts hide the token, head, or feature-level pattern you need.

Keep tensors near compute

The worker retains full activations. The UI requests only a bounded slice of 64, 256, or 512 values, avoiding a large browser transfer.

  1. Run the case and select a captured hook.
  2. Set token position; -1 means the final prompt token.
  3. For attention tensors, set the head index.
  4. Choose the smallest useful value limit and inspect the activation.
  5. Compare top values, features, tokens, or differences with the control run.
Scope check

A slice is not the full tensor distribution. Record the hook path, position, head, limit, dtype, and model revision so the view can be reproduced.

09 · EVALUATION

Turn a benchmark into debug cases

Use this to find recurring failures, regressions, anomalies, and internal signatures across examples.

Accepted sources

Import JSONL, CSV, JSON, or a Hugging Face dataset. Include prompt, reference prompt, expected behaviour, target, metric, and outcome columns when available.

  1. Name the benchmark and import a file or dataset ID.
  2. Filter passed, failed, regressed, anomalous, observed, or pending rows.
  3. Load the matching model and choose Run benchmark.
  4. Review outcome groups and clusters by output signature and internal circuit.
  5. Open a representative row and save it as a debug case for deeper analysis.
Current limit

A benchmark run processes at most the first 100 imported examples sequentially. Treat clusters as triage aids; inspect individual examples before inferring a shared mechanism.

10 · VALIDATION

Verify the intervention and export the record

Use this after an intervention appears to fix the selected case.

Guard against a local win

Verification reapplies the latest intervention to the selected example plus line-separated guardrail prompts, then labels outcomes as fixed, unchanged, or regressed.

  1. Keep the latest successful intervention selected.
  2. Add prompts whose behaviour must not regress, one per line.
  3. Choose Verify intervention.
  4. Review selected-case improvement and every guardrail outcome.
  5. Export the Markdown debug report with the case, metric, evidence, intervention, and results.
Research hygiene

Pin the model commit, chat template, prompt text, tokenisation, seed, dtype, device, metric, target, component path, scope, and intervention scale. A report is useful only if another run can recreate it.

11 · TROUBLESHOOTING

Read diagnostics before reading mechanisms

Numerical or runtime failures can imitate interpretability findings.

No worker

The graph still works. Start and connect local or Daytona execution for hooks.

Model mismatch

Load the currently inspected checkpoint into the worker before running.

Missing metric target

Target probability, logit difference, and token-group metrics require their matching fields.

NaN / Inf

Stop interpreting the run. Check precision, intervention scale, input length, and model compatibility.

Hook gaps

Unsupported module naming may limit capture. Use the inventory to confirm what was actually measured.

Latency or memory

Reduce model size, sequence length, capture scope, benchmark size, or activation slice limit.

Before you publish a finding

Evidence discipline, every time.

  • Pin model revision and resolved commit.
  • Save exact prompts, tokenisation, metric, target, and expected behaviour.
  • Use a matched reference and negative-control components.
  • Label graph facts, observations, and interventions separately.
  • Reserve causal language for controlled manipulations.
  • Test multiple examples, seeds, thresholds, and guardrails.
  • Export a report while the run context is still intact.
